Career Search Coach · Main App Architecture

Thinking About The App Like A System Designer

This report explains the public Career Search Coach app as a software system: how state moves, why the API is shaped the way it is, how LangGraph orchestrates backend work, and what a product builder needs to understand to make architecture decisions without writing every line of code.

1. Executive Mental Model

The main app is best understood as a stateful workflow with a human approval loop. The user is not just filling out a form; they are moving a run through a sequence of increasingly expensive and irreversible decisions: parse the resume, infer profile, capture preferences, generate a search brief, propose strategy, run external search, score jobs, and save feedback.

Input layer

Collects raw user intent: resume text, preferences, edited search lanes, and feedback labels.

State transition layer

Transforms one valid snapshot of the run into the next valid snapshot.

Decision output layer

Displays structured artifacts: profile, brief, strategy, ranked jobs, explanations, and tracker rows.

The most useful angle is not “frontend calls backend.” It is “the product is a controlled state machine.” Each button either changes local UI state, sends the current run state to the backend, or accepts a new state snapshot returned by the backend.

Software engineering lesson: most product bugs are state bugs. A user sees stale resume text, a tab unlocks too early, a cached run leaks across browsers, or search runs with outdated preferences. Good system design starts by deciding which component owns which state and what transitions are allowed.

2. Component Map

Each major component has a clean responsibility. The frontend manages interaction and display. FastAPI is the boundary layer. The backend modules do parsing, orchestration, search, scoring, caching, and export.

ComponentResponsibilitySystem-design interpretation
React frontend Owns the visible workflow, form state, filters, tabs, and local persistence. The presentation and interaction layer. It should be fast, reversible, and user-friendly.
FastAPI Exposes narrow endpoints and prepares state for browser-scoped caching. The boundary layer. It protects the backend from browser details and protects the browser from server paths.
LangGraph/backend modules Run staged profile, brief, strategy, search, scoring, feedback, and export work. The data-processing and decision layer. Similar to a multi-step ETL/ML pipeline.
OpenAI + SerpApi Provide model reasoning and job-source data. External dependencies. They add capability but also cost, latency, and failure modes.
Local JSON cache Stores graph state and artifacts for replay. A lightweight persistence layer. Good for MVP, not a durable multi-user database.

3. End-To-End Workflow

The app avoids running everything automatically. Instead, it splits the process into checkpoints so the user can inspect profile extraction, edit preferences, approve a brief, edit search lanes, and only then spend time and API cost on search/scoring.

This staged design is important. If the app ran the whole pipeline immediately after resume upload, a bad profile extraction or vague preference would waste search calls and produce noisy scores. The workflow makes intermediate artifacts visible so mistakes can be corrected before expensive stages run.

4. State Is The Architecture

State is the most important concept in this app. A system can have beautiful UI and strong model prompts, but if state ownership is unclear the product becomes unreliable. In this app, there are three important state layers: browser state, request/response state, and backend graph state.

The three state layers

LayerWhere it livesWhat it should containWhat can go wrong
UI state React component state and localStorage Current tab, form fields, visible filters, selected job, locally restored run snapshot. Stale browser data, a tab unlocking too early, local draft state disagreeing with backend output.
Transport state JSON payload sent to FastAPI The current run snapshot plus the user edit for this action, such as preferences or approved queries. Client sends stale or malicious fields, or an old cache path that should no longer be trusted.
Backend state GraphState inside Python Validated artifacts: profile, preferences, brief, strategy, raw jobs, normalized jobs, scored jobs, diagnostics. A downstream step reads fields that are missing, stale, or semantically incompatible.

The backend state is a TypedDict called GraphState. It is not a class with methods. It is closer to a shared, structured envelope. Every backend node reads some keys and returns updates for other keys. 

GraphState ~= {
  resume_text,
  candidate_profile,
  inferred_preferences,
  career_brief,
  search_strategy,
  approved_strategy,
  serpapi_results,
  normalized_jobs,
  deduped_jobs,
  sponsorship_assessments,
  scored_jobs,
  query_diagnostics,
  run_trace,
  errors,
  cache_run_path
}

State invariants

An invariant is a rule that should remain true if the app is healthy. Good product builders learn to ask “what must always be true?” because those rules are where bugs hide.

Resume before profile: candidate_profile should not exist without usable resume_text.
Preferences before brief: a brief is meaningful only after the app has inferred_preferences.
Brief before strategy: query lanes should be generated from the approved thesis, not directly from raw resume text.
Approved strategy before search: search should run only after the user has accepted or edited query lanes.
Scored jobs after normalized jobs: the scorer needs normalized, deduped postings and descriptions.
Server paths stay server-side: the browser sees cache_run_id, not cache_run_path.

Why state clearing matters

When preferences change, old downstream artifacts become suspect. A prior brief, strategy, and scored job list may no longer reflect the new goal. That is why the API clears downstream outputs after preference updates. This is a common architecture pattern: when upstream state changes, invalidate downstream derived state.

Product-builder lesson: every generated artifact has lineage. If the user changes the inputs, you must know which outputs are still valid, which should be recalculated, and which should be hidden until regenerated.

Browser-scoped replay

The public app uses an anonymous browser cookie named career_agent_browser_id. The backend hashes that cookie and stores runs under a folder for that browser. JavaScript does not read the cookie; the browser simply includes it with API calls.

This is privacy partitioning, not login security. It prevents casual cross-user leakage on the same public URL, especially between normal and incognito browsers. It does not create durable user accounts, permissions, or database-level authorization.

5. The App As A State Machine

A state machine is a system where only certain transitions are allowed. You can think of the tabs as the visible version of the state machine, and GraphState as the data version of it.

This mental model explains why the UI disables later tabs until earlier steps are complete. It also explains why “start over” must clear both local UI state and resume textarea state: otherwise the machine visually resets, but hidden data remains.

A stronger future version could make this state machine explicit in the backend: each run could have a canonical status, allowed transitions, and audit logs. For the MVP, the combination of UI checks, API clearing logic, and cached state snapshots is enough.

6. API Boundary: Contracts, Trust, And Ownership

The main API does not expose one giant “run everything” endpoint to the React app. Instead, it exposes step-specific endpoints such as /api/profile, /api/coach-brief, /api/strategy, and /api/search.

What the frontend controls
  • Which step is active
  • Form edits and selected filters
  • When the user approves a transition
  • How results are displayed and paginated
What the backend controls
  • Validation and structured models
  • LLM calls and external search
  • Cache write/read locations
  • Final scoring and export formats

In systems terms, the API boundary is a contract. The browser sends state plus the user’s latest edit. The server returns a new state snapshot with sensitive server paths removed.

The API does three jobs

Translate browser intent into backend state: the UI sends “save these preferences” or “run these approved queries,” not “call these internal functions.”
Defend server-owned state: the API ignores client-supplied cache_run_path and resolves run IDs only inside the current browser scope.
Return a safe public shape: backend state includes internal paths and implementation details, but the response exposes only user-safe identifiers.
Browser action:
  POST /api/search
  { state: currentGraphState, queries: editedQueries }

API responsibilities:
  1. attach browser-scoped cache path
  2. validate query objects
  3. mark strategy as approved
  4. run approved-search graph entrypoint
  5. strip server-only fields before returning JSON

A good API boundary is not just a route list. It is a trust boundary. The browser is allowed to express user intent, but the server decides where data is saved, which schemas are valid, and which backend steps are allowed to run.

7. LangGraph: Orchestration, Not Magic

LangGraph is important because this app is not a single prompt. It is a workflow with branching, persistence, intermediate artifacts, fallbacks, and human approval. LangGraph gives the backend a formal way to describe nodes, edges, conditional transitions, and shared state.

ConceptWhat it means hereWhy it matters
Node A backend step such as extract_candidate_profile, execute_search, or score_jobs. Each node has a focused responsibility and returns only the state updates it owns.
Edge The allowed transition from one node to the next. The workflow is explicit rather than hidden inside one long function.
Conditional edge A branch that decides whether to execute search or stop at summary. The graph can model human approval and skip expensive work until allowed.
State update A node returns a partial dictionary such as {"candidate_profile": ...}. The system composes small updates into one larger run state.
Entrypoint A function that runs only part of the graph for the current UI step. The frontend can request profile, brief, strategy, or approved search separately.

Why partial graph entrypoints exist

The original graph can describe the full workflow, but the React app should not run the full workflow on every click. The backend therefore provides narrow entrypoints:

run_resume_profile: parse/extract only enough to show the user their resume profile.
run_coach_brief: produce the search thesis without strategy/search execution.
run_search_strategy: create editable query lanes without spending SerpApi/scoring budget.
run_approved_search: run only the expensive search/scoring path after user approval.

This is a software architecture pattern: keep the domain workflow centralized, but expose product-friendly slices of it through the API. The product gets responsiveness and control; the backend keeps consistent business logic.

Structured outputs are contracts

OpenAI calls are not free-form text completions here. The app asks the model to return JSON matching Pydantic schemas, then validates it. That means model output becomes a typed contract, not a blob of prose. 

LLM prompt + schema
        ↓
OpenAI structured response
        ↓
Pydantic validation
        ↓
Python model dump
        ↓
GraphState update

Product-builder lesson: AI features become much easier to operate when model output is structured, validated, and stored as state. The user can still see prose explanations, but the system should reason over fields.

8. Failure Modes, Observability, And Recovery

A system designer cares about the unhappy path because failures are also state transitions. The happy path is a demo. The real product is what happens when a model returns invalid JSON, a job search returns zero results, a cached run is missing fields, or the user changes upstream inputs after downstream artifacts already exist.

A useful framing is: for every failure, decide whether the system should retry, fall back, stop and ask the user, or continue with a warning. That decision should be explicit because it changes what state the next step is allowed to trust.

Failure typeExample in this appCurrent mitigationSystem-design question
Schema / validation failure OpenAI returns text that does not match the expected Pydantic model. Structured output parsing, validation, and error collection in state. Should the step retry, fail visibly, or use a deterministic fallback?
External dependency failure SerpApi quota fails, OpenAI latency spikes, or job descriptions are sparse. Query diagnostics, visible errors, cached artifacts, and conservative fallback labels. Can the user recover without losing work? Can we tell which dependency failed?
Stale derived state User changes preferences after a brief, strategy, and scored jobs already exist. Downstream artifacts are cleared or regenerated from the latest upstream state. Which downstream fields are now invalid, and which can safely remain?
Partial run artifact A run has a profile and preferences but no results because the search failed or stopped. Cache loading is tolerant of missing fields and the UI shows step completion separately. Does replay show what happened, or does it pretend the run is complete?
Model uncertainty Sponsorship status is unclear because most postings do not explicitly state it. Unclear is treated as evidence status inside match fit, not as a hard result-list badge. Is this label a fact, an inference, or an absence of evidence?
Cost / latency pressure Searching and scoring many jobs takes time and external API budget. Human approval before search, query limits, batching, and cached runs. Where should we spend money only after user intent is clear?

The core software engineering idea is that failure handling should preserve truth. If the app cannot know sponsorship status, it should say that. If a cached run is partial, it should load as partial. If a model response fails validation, that should not silently become trusted product state.

What the app already logs or preserves

errors: user-visible or developer-visible messages appended to state when a backend fallback is used.
query_diagnostics: per-query result counts and errors, useful for debugging bad search lanes.
run_trace: timing and count events for approved search steps, useful for latency and cost reasoning.
Cache artifacts: raw search rows, normalized jobs, deduped jobs, scored jobs, and final state are saved separately.

What “production-grade” would add

A larger version would add structured logs, metrics dashboards, background job status, alerting, request IDs, cost tracking by run, and eval datasets for scoring quality. The lesson is that architecture is not only about moving data. It is about knowing when the system is wrong, preserving enough evidence to investigate, and giving the user a path forward.

Product-builder lesson: every non-trivial app needs a recovery model. “Try again” is not a recovery model unless the system knows what failed, what state remains valid, and what work would be repeated.

9. Product Architecture Tradeoffs

Architecture is the art of choosing what to make easy now, while keeping a clear path for what must become more durable later. The current app makes excellent MVP choices, but each choice has a known breaking point.

Current choiceWhy it is right for this MVPWhat breaks laterLikely upgrade
React frontend instead of Streamlit The product needs a controlled workflow, rich results view, filters, tracker, and local state. More frontend complexity: state bugs, build tooling, API contracts, and UI regressions. Component tests, typed API client, stronger frontend state management if screens multiply.
FastAPI step endpoints Each user action maps to a clear backend operation and avoids running expensive work too early. Many endpoints can drift if they do not share the same state and validation rules. Generated API types, shared response envelope, explicit run status model.
LangGraph staged pipeline The workflow has natural stages, human approval, partial reruns, and structured intermediate state. Complex graph logic can become hard to inspect if nodes do too much or state grows without discipline. Node-level tests, explicit state versioning, graph visualizations, run traces in an operator UI.
Local JSON cache Fast to build, easy to inspect, easy to replay, no database setup. Harder concurrency, schema migrations, search/filtering, deletion policy, and backup strategy. Database-backed runs with migrations, retention policy, and row-level ownership.
Browser-scoped anonymous cookie Protects casual users from seeing each other’s cached runs without adding login friction. No identity recovery, no account transfer, no team access model, no strong authorization. Accounts, sessions, authorization checks, and explicit data deletion/export controls.
Synchronous search/scoring request Simple request-response flow is easier to reason about for a small app. Long-running requests can time out, block retries, and make progress hard to show. Background jobs, polling or server-sent events, resumable run status.
Structured LLM output Turns model responses into typed state instead of unbounded prose. Schema evolution and model behavior changes need compatibility checks. Versioned schemas, eval suites, regression fixtures, and model/prompt release discipline.

How to think like a system designer

Do not ask only “does the feature work?” Ask “what owns the truth?”, “what happens if this runs twice?”, “what data becomes invalid when this changes?”, “what evidence do we keep?”, and “what is the cheapest architecture that does not corner us?” Those questions are more important than any specific framework.

10. What A Hybrid Product Builder + System Designer Should Be Good At

You do not need to write every line of code to reason well about this system. You do need to ask the right questions about state, contracts, latency, cost, trust boundaries, and user workflow. The strongest product builders understand enough software architecture to decide where product behavior should live.

SkillWhat it meansHow it appears in this appGood question to ask
State modeling Knowing what exists, what is derived, what is persisted, and what is currently authoritative. Browser draft state, backend GraphState, cached artifacts, selected result filters. “If this user edits preferences, which outputs become invalid?”
Contract thinking Defining what each boundary accepts, returns, hides, validates, and refuses. FastAPI request/response models, safe run IDs, stripped server paths. “Can the browser send anything that the server should refuse or ignore?”
Workflow orchestration Breaking a product journey into allowed transitions, not just screens. LangGraph nodes/edges plus React tabs for resume, preferences, brief, strategy, results. “Where should we force approval before running an expensive or noisy step?”
Invalidation and lineage Tracking what generated each artifact and when downstream output must be cleared. Preference changes clear brief/strategy/results; approved queries create scored jobs. “Which state was this output based on, and is that input still current?”
Trust boundaries Separating what the client may request from what the server must decide. Browser cookie is HttpOnly; API ignores client-supplied cache paths; cache is browser-scoped. “What would be dangerous if the browser could control it directly?”
Failure design Planning what users and operators see when a dependency fails or output is uncertain. Errors, diagnostics, fallback labels, partial cache replay, explicit empty states. “What should happen if SerpApi returns zero jobs or the LLM fails validation?”
Observability thinking Deciding what traces, diagnostics, and artifacts must exist to debug a bad run later. run_trace, query_diagnostics, saved raw/normalized/scored job artifacts. “If a user says the results are bad, what evidence do we have to diagnose why?”
Scaling judgment Knowing when a simple design must become database/jobs/auth infrastructure. Local cache works for MVP; accounts, queues, and database become necessary with real traffic. “What breaks first if this goes from 5 users to 500?”
AI product judgment Separating model-generated display text from structured fields that drive product behavior. LLM prose explains matches; validated scores, actions, and evidence lists drive filters/results. “Which parts of the model output are for display, and which are allowed to drive behavior?”
UX as control surface Using UI controls to guide valid backend transitions rather than merely decorating data. Tabs, disabled states, continue buttons, strategy approval, filters, tracker actions. “Does the interface make the next valid system action obvious?”

The central habit is to think in lifecycle terms: what creates this state, who owns it, who can mutate it, who consumes it, how it is validated, how it is persisted, and what invalidates it.
